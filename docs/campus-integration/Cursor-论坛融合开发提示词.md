## 5. 架构和跨产品边界

### 5.1 身份与租户

- Account 是身份权威。跨产品仅用稳定 accountSub（usr_xxx），论坛自己的 User.id 保留本地投影及旧作者映射。不得按昵称、邮箱或手机号强行合并账号。
- 小程序的微信授权、手机号登录和绑定需求接入 Account 的真实能力；不复制参考源码 JWT、密码表、模拟验证码或 code-as-openid 作为生产登录。
- 每条校园业务必须有明确 spaceId/universityId/campusId；学校来自后端授权上下文。创建、查询、详情、附件、互动、后台、通知、搜索和统计全链路隔离，不能只在前端下拉框筛选。
- 用户自行填写学校不等于学校认证通过；原学校认证和旧成员兼容由明确规则决定。新增认证不能静默撤销已有合法成员权限。
- 非高校圈子/同城/单位继续可用，可按配置开启适合的服务，不能被要求补学生证才能使用原论坛。

### 5.2 消息与通知

- 已核查 yydsxwh/kkchat README：POST /api/service/direct、POST /api/service/messages、GET /api/service/unread?accountSub=usr_...；服务端携带服务凭证和 X-KKChat-Product。浏览器不得拿到服务 token。
- 先读当前 Shared 的 kkchat-client 与 KKChat 群接口，再决定业务群接入方式。缺能力时补受支持接口，不在论坛和参考 Express 后端各维护一份聊天权威数据。
- 旧聊天迁移要有 accountSub 映射、消息/附件校验、演练、增量同步和回滚；未映射身份不得猜测归属。
- 公开论坛、仅本校帖子、树洞、私信和证书材料采用不同通知摘要规则，避免从通知或微信模板泄漏隐私。

### 5.3 存储、支付和公共能力

- 沿用我们现有媒体上传、OSS/存储策略，附件记录所有者、业务归属和可见性。公开内容和认证证明、证书、投诉证据不能共用无需鉴权的静态 URL。
- 参考源码没有完整支付/退款/对账/托管链路。“价格”“押金”“悬赏”字段不是已支付订单。若本轮引入真实收付款，走已验证可用的统一支付服务，补订单、回调验签、幂等、退款和对账，绝不造第二套余额账本。
- Platform README 当前明确标注主要能力 NOT_DEPLOYED，并要求不要自动部署 Platform 生产。先核实可用性；允许用适配层保留当前已验证路径，不能假装依赖已上线，不能擅自部署整个公共平台。
- 不做无必要的微服务集群或基础设施改造。论坛独立运行候选的数据库、私有附件目录和进程边界须先验收，再决定正式切流。

### 5.4 数据建模

- 普通讨论继续使用 ForumPost/ForumComment/ForumAction/ForumZone。校园服务有公共内容记录和结构化业务实体，避免仅靠一个 extra JSON 驱动所有状态。
- 建议实体：CampusServiceListing、CarpoolTrip/Participant、ServiceTask/Assignment、MarketplaceListing、RentalRequest、LostFoundRecord、AnonymousPost/Comment、DirectoryEntry、ResourceItem、GuideItem/Checkin、AchievementSubmission、Canteen/Stall/Review、CampusMap/POI、AcademicCalendar/Event、Complaint/Timeline、CreditLedger、ModerationCase。名称可按仓库规范调整，不强迫照抄本建议。
- 统一金额最小货币单位、时区/UTC存储约定、分页上限、状态枚举、软删除、审计和幂等键；关键唯一约束由数据库保证。
- 不要求把现有 SQLite 一次性换成 MySQL。先验证当前部署数据库，再做有证据的容量与并发选择；若迁移数据库，单独写可回滚方案并保持原数据。

## 7. 必须实现的核心业务状态与权限

- 拼车：草稿/发布/满员/截止/结束/取消；加入与取消必须原子、幂等。变更人数不能小于实际参与人数；结束只能由有权角色操作。记录完成或取消原因。
- 任务/快递/打印/代办：草稿→待审核/可接单→已承接→履约中→待确认→已完成；取消/超时/争议为明确分支。接单者不能接自己任务，完成应有发布方确认或明确超时规则。
- 二手：在售/预留/售出/下架；租赁：可租/预订/交付/租用中/归还确认/结束/争议。不要把closed一值混用为“已接单”“已完成”“被下架”。
- 失物：寻找中/招领中/核验中/已找回/已关闭；个人证件图片与领取证明须限制访问。
- 树洞：草稿/待审/已发布/驳回/下架/删除；评论单独审核与删除。匿名展示与管理员追溯权限分离，匿名标识按学校/帖子范围设计以降低跨场景关联。
- 成就：未提交/待审/通过/驳回/重提，服务端为状态权威，上传失败和审核并发有明确处理。
- 评价与信用：只有完成的业务关系可评价；防重复、撤销和申诉；信用扣分不能由普通用户直接触发任意目标封禁。原论坛发言权与校园服务信用限制分开配置。
- 所有权限同时在页面、API、资源访问层落实；按钮隐藏不能作为鉴权。
